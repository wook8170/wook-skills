# 산출물 세트 구성 — 권 · 분류 · 표지 · 요구사항 ID · 추적

## 1. 권 목록(국내 SI · GS 인증 관행)

기준 저장소의 42권을 분류별로 묶은 목록이다. 새 저장소는 이 목록에서 제품에 맞는 권만 고른다. 고르는 순서는 `bootstrap.md` 에 있다.

| 분류 | 권 |
|---|---|
| 기획 | 제품 기획서 · 요구사항 정의서 · 기능 명세서 |
| 아키텍처 | 시스템 아키텍처 설계서 · 데이터 설계서 · 보안 설계서 · 배포 · 운영 구성 설계서 |
| 개발 설계 | 서버 모듈 설계서 · 웹 앱 설계서 · 엔진(집계 · 실시간 등) 설계서 · 프로그램 목록 · 코딩 컨벤션 · 개발 가이드 · 메시지 · 오류 코드 정의서 |
| 디자인 | 디자인 시스템 가이드 · 화면 설계서 · UI 가이드(화면 작성 · 문구 · 접근성) |
| 규격 | API 규격서 · SDK · 임베딩 규격서 · CLI 규격서 · 커넥터 규격서 · 외부 연계 인터페이스 정의서 |
| 시험 | 시험 계획서 · 시험 결과서(단위 · 통합 · e2e · 성능) · 시험 케이스 명세서 |
| 데이터베이스 | DB 표준화 정의서 · DB 인덱스 · 성능 설계서 · DB 운영 · 점검 · 백업 절차서 · CRUD 매트릭스 |
| 모델링 | 유즈케이스 명세서 · 클래스 · 시퀀스 다이어그램 설계서 |
| 보안 | 보안 취약점 점검 · 조치 내역서 · 역할별 권한 매트릭스 · 개인정보 처리 흐름도 |
| 추적 | 요구사항 추적표 |
| 운영 | 배치 작업 정의서 · 장애 대응 절차서 |
| 품질 | 오픈소스 사용 목록 · 라이선스 검토서 · 웹 접근성 점검 결과서 · 정적 분석 · 소스 품질 결과서 |
| 사업 관리 | 형상 관리 계획서(브랜치 · 버전 정책) · 이행 · 전환 계획서 · 교육 계획서 |

## 2. 권 대장과 번호

- 권 대장 한 파일(`catalog.json`)에 `categories`(분류 순서)와 `books`(`id` · `category` · `title`)를 둔다.
- 번호는 고정이다. 새 권은 맨 끝 다음 번호로 더하고, 지운 번호를 다시 쓰지 않는다. 권을 없앨 때는 행을 지우지 않고 권 메타의 `status` 를 「폐기」로 바꾼다.
- 그래서 번호 순서와 분류 순서는 다를 수 있다. 통합본은 분류 순서로 묶고, 분류 안에서 번호 순서로 싣는다.
- 권 ID 형식 예: `<접두>-DD-<두 자리>`. 권 폴더는 `<권 ID>-<영문 slug>/`.

## 3. 권 폴더 구성

| 위치 | 손으로 쓰는가 | 내용 |
|---|---|---|
| `book.json` | 쓴다 | 권 메타. 필수 키 `id · category · title · slug · edition · status · syncedCommit · chapters · xlsx · related · revisions` |
| `<두 자리>-<이름>.md` | 쓴다 | 장 원고. 장 하나 = 파일 하나. 부록은 `A1-<이름>.md` + `"appendix": true` |
| `<두 자리>-<이름>.gen.md` | 생성 | 코드 · 데이터에서 뽑은 전수 목록 장 |
| `figures/` | 쓴다 · 일부 생성 | 다이어그램 원본(텍스트)과 캡처 PNG |
| `data/` | 필요할 때만 쓴다 | 코드로 바로 뽑을 수 없는 원천 데이터(JSON). 행마다 근거 소스를 적는다 |

`book.json` 의 칸 뜻:

| 칸 | 뜻 | 바꾸는 때 |
|---|---|---|
| `edition` | 이 권이 설명하는 제품 버전 | 다른 버전 기준으로 다시 맞출 때 |
| `status` | 초안 · 검토 · 확정 · 폐기 | 검토 · 승인 단계가 바뀔 때 |
| `syncedCommit` | 이 권의 사실과 맞는 코드 커밋(앞 10자) | 근거 소스를 다시 읽고 내용을 맞췄을 때만 |
| `revisions` | 개정 이력(버전 · 날짜 · 한 줄) | 장을 더하거나 내용을 크게 고칠 때 |
| `chapters[]` | `file · title · summary · sources`(+ 생성 장이면 `generator · options`) | 장 · 근거가 바뀔 때 |

`syncedCommit` 을 근거를 읽지 않고 옮기면, 검사기가 바뀐 근거를 더는 보여 주지 않는다. 그러면 낡은 내용을 찾을 수 없게 된다.

## 4. 장 원고 규칙

- 맨 위 주석에 근거 소스(저장소 상대 경로)를 적는다: `<!-- sources: a/b.ts, docs/x.md -->`. 검사기가 경로가 실제로 있는지 본다.
- 제목은 `##` 장 → `###` 절 → `####` 소제목 세 단계만 쓴다. 장 · 절 번호는 조판할 때 붙이므로 원고에 적지 않는다.
- 서식은 문단 · 글머리 목록 · 번호 목록 · 코드 블록 · 표 · 인용 · 굵게 · 코드 조각만 쓴다.
- 그림은 `[[그림 <장>-<순번> | <원본 파일> | 설명]]` 한 줄로 참조한다. 원본이 없으면 검사기가 오류로 잡는다.
- 문체는 「~한다」 평서체다. 「해요」체 · 「합니다」체는 검사기가 잡는다. 「 」 안의 화면 문구와 코드는 검사하지 않는다.
- 아직 구현하지 않은 기능은 「계획 기능」 절에 따로 두고, 구현된 것처럼 쓰지 않는다.
- 단위마다 고정 서식(모듈 · API · 테이블 · 화면 · 컴포넌트)을 채우고, 빈 항목은 「해당 없음」으로 적는다.

분량 하한(공백 · 주석을 뺀 글자 수, 생성 장 포함, 기준 저장소의 값): 설계서 4만 자, 기획 · 안내 2만 자, 규격 · 목록은 하한 없음. 권 메타의 `volumeClass`(`design` · `plan` · `spec`)로 등급을 바꾼다.

권 머리(첫 장)에는 생성 장마다 「대상 <대상> N개 중 N개 수록」을 적는다. 흐름 생성 장이면 「흐름 N개 중 N개 수록」이다. 검사기가 이 표기를 확인한다.

## 5. 표지 · 배포 등급

- 설계 산출물은 **대외비 · 사내 보관**이다. 그래서 조판 출력 자리를 고객 배포 문서 자리와 나누고, 인자 없는 조판 명령은 배포 문서만 굽게 한다.
- 표지에 문서 번호 · 제목 · 적용 버전 · 발행처 · 배포 등급(「대외비 · 사내 보관」)과 결재 칸(작성 · 검토 · 승인)을 둔다.
- 문서 정보 쪽에 개정 이력 · 대상 독자 · 관련 권을 둔다. 표지 · 차례 · 책갈피 구현은 `pdf-typeset`.

## 6. 요구사항 ID 체계

유형마다 접두를 두고 번호를 붙인다. 기준 저장소의 형식은 다음과 같다.

| 유형 | 형식 | 원천 |
|---|---|---|
| 기능 | `REQ-F-<세 자리>` | 기능 원장 CSV 의 대분류 · 중분류 묶음(생성기가 묶음마다 하나를 만든다) |
| 원장 뒤 추가 기능 | `REQ-FX-<두 자리>` | 원천 데이터 `data/requirements.json` |
| 비기능 | `REQ-PER` · `REQ-SEC` · `REQ-SIR`(인터페이스) · `REQ-DAR`(데이터) · `REQ-OPS` · `REQ-QUR`(품질) · `REQ-TER`(시험) · `REQ-ECR`(장비 구성) · `REQ-CMP` · `REQ-ACC` · `REQ-DOC` + `-<두 자리>` | 같은 원천 데이터 |
| 제약 | `CON-<두 자리>` | 같은 원천 데이터 |

- 비기능 접두는 NIPA 요구사항 분류 코드(SFR · PER · SER 등)와 대응시키고, 분류 기준 장을 따로 둔다.
- ID 는 한 번 붙이면 다시 쓰지 않는다. 요구사항을 없애면 행을 지우지 않고 상태를 「폐기」로 바꾼다.
- 기능 요구사항은 손으로 쓰지 않는다. 기능 원장을 고치면 요구사항 목록도 생성기로 따라 바뀐다.
- 원천 데이터 행마다 근거 소스 경로를 적고, 검사기가 경로를 확인한다.

## 7. 추적(요구사항 → 기능 → 화면 → 시험)

- 추적표 권은 원천 데이터(`trace.gen.json` 같은 생성 JSON)에서 만든다. 화면 ID(`SCR-<영역>-<번호>`), 유즈케이스, 시험 케이스 ID 를 요구사항 ID 로 잇는다.
- 끊긴 연결을 네 종류로 센다: 시험 케이스가 없는 요구사항 행 · 화면이 이어지지 않은 기능 행 · 요구사항에 닿지 않은 화면 · 요구사항에 닿지 않은 유즈케이스.
- 종류마다 기준선 파일과 비교해 늘면 실패한다(래칫). 줄었으면 기준선을 다시 잠그고, 늘었을 때는 기준선을 올리지 않는다. 연결을 채울 수 없으면 결정권자 확인을 받는다.
- 화면 ID 는 화면 설계서뿐 아니라 유즈케이스 · 추적표 · 시험 케이스 권에서도 쓴다. 그래서 화면 ID 를 바꾸면 그 권들의 행도 같은 변경에서 고친다(`screen-design.md`).
- 권한 매트릭스는 서버 라우트 × 역할 표를 생성하고, 칸 값은 「허용 · 거부 401 · 거부 403 · 멤버십 따름」처럼 응답으로 적는다. 화면 설계서와 시험 계획이 이 칸 값을 인용한다.
