# 설계 산출물 · 개발 문서 세트

국내 SI · GS 인증 관행의 설계 산출물을 **코드에서 뽑는 부분과 사람이 쓰는 부분으로 나눠** 만들고, 기능이 바뀔 때마다 같은 변경에서 맞춘다.
이 방식은 한 BI 제품 저장소의 설계 문서 세트(42권)에서 쓰던 체계를 일반화한 것이다. 참고 문서의 「기준 저장소」는 그 저장소를 말한다.

## 0. 먼저 볼 것

- 프로젝트 설정 파일(`.claude/skills-config/design-deliverables.md`)이 있으면 그 저장소의 경로 · 명령 · 권 번호 체계 · 함정을 먼저 읽고 따른다.
- 설정 파일이 없으면 산출물 세트가 이미 있는지 찾는다. 있으면 그 체계를 따르고, 없으면 `reference/bootstrap.md` 로 최소 구성부터 세운다.
  ```bash
  rg -a -l -i 'catalog\.json|요구사항 정의서|화면 설계서|traceability|book\.json' -g '!node_modules' .
  ```
- PDF 조판 · 차례 · 책갈피 · 가로 쪽 · 그림 배율 · 다이어그램은 **`pdf-typeset` 스킬**을 쓴다. 이 스킬에서 다시 설명하지 않는다.
- 문장 기준의 정본은 `readable-korean` 스킬의 `reference/report-writing-rules.md` 이고, 마감 점검은 `readable-korean` 스킬로 한다.

## 1. 하는 일별로 읽을 문서

| 하는 일 | 읽을 문서 |
|---|---|
| 산출물 세트 구성 · 권 번호 · 분류 · 표지 · 요구사항 ID · 추적 | `reference/deliverable-set.md` |
| 생성 장(`*.gen.md`) · 원천 데이터 · 엑셀 · 색인 · 통합본 · 검사(래칫) | `reference/generation-pipeline.md` |
| 화면 설계서(SI 화면기획서 양식, 스토리보드 · 화면 항목 원장) | `reference/screen-design.md` |
| 디자인 시스템 견본 그림(토큰 · 프리미티브 · 컴포넌트를 실제 CSS 로 2x 렌더) | `reference/ds-specimen.md` |

## 2. 판단 기준(모든 작업 공통)

1. **코드에서 셀 수 있는 목록은 손으로 쓰지 않는다.** 생성기가 장 · 엑셀을 만들고, 사람은 그 위에 설계 이유 · 제약 · 흐름 해설만 쓴다.
2. **생성물은 손으로 고치지 않는다.** 머리 해시와 재생성 비교 검사로 막는다. 틀렸으면 생성기나 원천을 고친다.
3. **요구사항 ID 가 먼저다.** 기능 변경은 요구사항 ID → 설계 권 → 시험 케이스 순으로 이어지고, 끊긴 수를 래칫으로 센다.
4. **숫자는 세어서 쓴다.** 다른 문서 값을 베끼지 않는다. 소스로 정할 수 없는 값만 `> **예정**: <언제 · 어디서 채우는지>` 로 둔다. 「미확인」은 쓰지 않는다.
5. **사실은 한 권에 한 번만 쓴다.** 다른 권의 사실은 「<권 번호> <장> 참조」로 잇는다.
6. **개발 과정의 흔적을 남기지 않는다.** 작업자 · 작업 묶음 이름, 에이전트 지침 파일, 작업 로그를 문서 근거로 들지 않는다(목록은 `reference/writing-rules.md`).
7. **긴 목록은 엑셀로, 넓은 표는 그 쪽만 가로로, 모든 PDF 는 차례 · 책갈피를 단다.** 방법은 `pdf-typeset`.

## 3. 마감 전 확인

- [ ] 바뀐 기능의 요구사항 ID 를 정했고, 커밋 · PR 본문에 적었다(무관하면 「요구사항 해당 없음」)
- [ ] 영향 권의 생성 장 · 원천 데이터 · 엑셀 · 색인을 다시 만들었다(손으로 고친 생성물 0)
- [ ] 산출물 검사(재생성 비교 · 추적 래칫 · 정합 검사)를 통과했다. 래칫 기준선은 줄었을 때만 다시 잠갔다
- [ ] `writing-rules.md` 의 카운트 명령에서 「미확인」 · 개발 흔적 · 버전 뜻 「판」이 0 이다
- [ ] 손으로 쓴 장은 `readable-korean` 스킬로 점검했다
- [ ] 무엇을 돌렸고 무엇을 건너뛰었는지 근거와 함께 보고에 적었다
