# code-structure-guard — 코드 구조 상한과 래칫

큰 파일과 긴 함수는 한 번 생기면 줄이기 어렵다. 리팩토링 비용은 쌓인 크기에 비례해서 커진다. 그래서 이 스킬은 두 가지를 지킨다.

1. **새 코드는 상한을 지킨다.**
2. **이미 상한을 넘은 파일 · 함수는 늘리지 않는다.** 래칫의 허용 폭은 파일 +20줄 · 함수 +10줄뿐이고, 복잡도 · 훅 수 등 다른 수치는 허용 폭이 없다. 고칠 곳이 큰 함수 안에 있으면, 고치는 부분을 하위 함수 · 훅 · 하위 컴포넌트로 빼낸 뒤 고친다.

저장소에 래칫 검사가 있으면 그 결과가 판정 기준이다. 없으면 `reference/ratchet.md` 로 세운다. 저장소마다 다른 값(래칫 명령 · 검사 범위 · 예외 폴더 · 기준선 수치 · 로거 위치)은 프로젝트 설정 파일에 적는다. 설정 파일이 있으면 그 값이 이 문서의 기본값보다 먼저다.

## 기본 상한

| 항목 | 경고 | 실패 | 비고 |
|---|---|---|---|
| 일반 함수(로직 · 서비스 · 유틸) 줄 수 | 60 | 100 | |
| 컴포넌트 함수 줄 수(JSX · 템플릿 포함) | 150 | 300 | React 함수 컴포넌트, Vue `<script setup>` + `<template>` |
| 서버 라우트 처리 함수 줄 수 | 80 | 150 | 라우트 정의에 넘긴 함수 |
| 파일 줄 수 | — | 500 | 시험 · 생성물 · 데이터 표 · 선언 파일 제외 |
| 기존 위반의 허용 폭 | — | 파일 +20 · 함수 +10 | 기준선에 있는 것만. 새 파일 · 새 함수 · 다른 수치는 0 |
| 순환 복잡도 | — | 15 | 분기(`if` · `case` · 반복 · `catch` · `?:` · `&&` · `\|\|` · `??`) + 1 |
| 블록 중첩 깊이 | — | 4 | ESLint `max-depth` 기준, `else if` 는 더하지 않음 |
| 컴포넌트가 직접 부르는 훅 | — | 20 | `use*` 호출 |
| 라우트 파일 한 개의 라우트 수 | — | 15 | |
| 라우트 처리 함수의 DB 직접 호출 | — | 0 | 새 라우트부터. 서비스 · 저장소 모듈을 거친다 |
| 서버 소스 최상위의 새 파일 | — | 0 | 도메인 폴더 아래에 둔다 |
| 새 순환 의존 | — | 0 | 값 import 기준(타입 전용 · 동적 import 제외) |
| 새 빈 `catch` · 버리는 `.catch(() => {})` · `console` | — | 0 | 명령행 도구의 출력은 예외 |

시험 파일 · 생성물 · 데이터 표(코드 표, 지역 경계 같은 상수 묶음)는 길이 상한에서 뺀다. 다만 시험도 한 함수가 지나치게 길면 시나리오별로 나눈다.

## 언제 나누나

- **함수**: 경고선을 넘기면 나눌 자리를 찾는다. 이름을 붙일 수 있는 단계(검증 → 조회 → 변환 → 저장)가 보이면 단계마다 함수로 뺀다. 같은 함수 안에 「무엇을 할지 고르는 분기」와 「실제 처리」가 섞여 있으면 분기만 남기고 처리를 뺀다.
- **복잡도 · 중첩**: 중첩이 3단을 넘으면 앞에서 빠져나가기(early return), 조건을 이름 있는 함수로 빼기, 분기 표(객체 · `Map`)로 바꾸기를 먼저 검토한다.
- **파일**: 파일이 400줄을 넘거나, 내보내는(export) 것들이 서로 다른 주제로 갈리면 주제별 파일로 나눈다. 한 파일에 화면 · 상태 · API 호출 · 변환 로직이 함께 있으면 역할별로 나눈다.
- **컴포넌트**: 훅이 10개를 넘거나 JSX 가 화면 한 쪽을 넘으면 하위 컴포넌트와 사용자 정의 훅(`useXxx`)으로 나눈다. 상태와 효과는 훅으로, 표시는 하위 컴포넌트로 보낸다. 앱 전체를 감싸는 셸에는 상태를 직접 두지 않고 스토어로 옮긴다.
- **라우트**: 라우트 파일 한 개는 한 자원(예: 데이터소스)만 다룬다. 처리 함수는 입력 검증 → 권한 확인 → 서비스 호출 → 응답 만들기만 하고, SQL · 외부 호출은 서비스 · 저장소 모듈이 맡는다.

## 폴더와 계층

- **도메인 폴더**: 서버 소스는 `backup/` · `license/` · `scheduling/` · `embed/` 처럼 업무 영역별 폴더에 둔다. 폴더 안은 `routes`(HTTP 입구) · `service`(업무 규칙) · `repo`(DB 접근) · `types` 로 나눈다. 최상위에는 앱 조립(`app.ts`)과 진입점만 둔다.
- **계층 방향**: 라우트 → 서비스 → 저장소 · 커넥터 한 방향으로만 import 한다. 아래 계층이 위 계층(특히 `routes/`)을 가져오면 안 된다. 여러 라우트가 쓰는 도우미는 `routes/` 가 아니라 서비스 계층에 둔다.
- **순환 금지**: 두 모듈이 서로 필요하면 공통 부분을 세 번째 모듈로 뺀다. 타입만 필요하면 `import type` 을 쓴다. 동적 import 로 순환을 숨기지 않는다.
- **공용 로직은 프레임워크와 무관한 패키지로**: 같은 순수 로직(계산 · 변환 · 검증 · 문구)을 두 화면 앱(React · Vue 등)이나 서버 · 화면이 함께 쓰면, 프레임워크를 모르는 공용 패키지에 한 벌만 둔다. 앱 안에는 프레임워크에 묶인 코드(컴포넌트 · 훅 · 스토어 연결)만 남긴다. 새 파일을 만들 때 다른 앱에 같은 이름의 파일이 있는지 먼저 확인한다.

## 오류를 버리지 않기

- 빈 `catch {}` 와 `.catch(() => {})` 를 새로 쓰지 않는다. 무시해도 되는 오류라도 로그 함수(구조화 로그 · 운영 로그 모듈)로 이유와 함께 남긴다.
- 감사 기록 · 결제 · 권한처럼 빠지면 안 되는 쓰기의 실패는 버리지 않고 경보 대상으로 올린다.
- 서버 · 화면 코드에서 `console.*` 대신 저장소의 로거를 쓴다. 명령행 도구의 표준 출력은 예외다.

## 작업 순서

1. 손대기 전에 대상 파일 · 함수의 지금 크기를 본다(래칫 보고 명령 또는 줄 수). 이미 넘었으면 이번 변경에서 늘리지 않을 방법(빼낼 하위 함수 · 훅 · 컴포넌트)부터 정한다.
2. 새 파일은 도메인 폴더 아래, 계층에 맞는 자리에 만든다.
3. 끝나면 래칫 게이트를 돌린다. 수치가 줄었으면 기준선을 다시 잠그고 같은 변경에 넣는다. 늘어난 값을 재잠금으로 덮지 않는다. 꼭 늘려야 하면 이유를 보고에 적고 오너 확인을 받는다.

## 서브에이전트 지시문에 넣을 문구

```
코드 구조 상한(code-structure-guard): 새 함수는 일반 100줄 · 컴포넌트 300줄 · 라우트 처리 함수 150줄,
새 파일은 500줄, 복잡도 15, 중첩 4, 컴포넌트 훅 20개를 넘기지 않는다. 이미 넘은 파일 · 함수는 늘리지 않는다(허용 폭 파일 +20 · 함수 +10줄) —
고칠 부분을 하위 함수 · 훅 · 하위 컴포넌트로 빼낸다. 새 라우트는 DB 를 직접 부르지 않고 서비스를 거친다.
서버 최상위에 새 파일을 두지 않는다. 순환 import · 빈 catch · console 을 새로 만들지 않는다.
공용 순수 로직은 프레임워크 무관 패키지에 한 벌만 둔다. 끝나면 구조 래칫 게이트(프로젝트 설정 파일에 적힌 명령)를 돌린다.
```
