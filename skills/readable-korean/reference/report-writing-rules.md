# AI 작성 보고서 인간화·정제 지침

## 1. 목적과 역할

문서를 새로 작성하지 않고, 기존 문서를 실제 회사 실무자가 작성한 최종 보고서처럼 편집한다.

독자는 개발자가 아니라 임원, 사업 담당자, 고객, 프로젝트 관리자 등 일반적인 업무 관계자로 가정한다.

다음 원칙을 반드시 적용한다.

## 2. AI가 작성한 흔적 제거

최종 문서에는 다음 내용을 남기지 않는다.

- “분석해 보겠습니다”, “검토 결과”, “다음 단계에서는”, “이제 ~를 살펴보겠습니다”처럼 AI가 작업을 수행하는 과정을 설명하는 문장
- 어떤 명령, 프롬프트, 에이전트, 스크립트, 도구를 사용했는지에 대한 내용
- “본 분석에서는”, “본 문서에서는”이 불필요하게 반복되는 문장
- “종합하면”, “결론적으로”, “요약하면”의 과도한 반복
- “핵심은 ~입니다”, “중요한 점은 ~입니다”와 같은 의미 없는 강조
- 작성자가 스스로 문서 품질을 평가하는 표현
- 독자에게 불필요한 작성 과정, 조사 과정, 사고 과정, 작업 로그
- TODO, 내부 메모, 작성 지시, 초안 흔적

문서에는 최종적으로 확인된 내용과 판단에 필요한 정보만 남긴다.

## 3. 사람이 작성한 업무 문서처럼 작성

문장은 자연스럽고 담백하게 작성한다.

AI 특유의 설명식 문장보다 실제 회사 보고서에서 사용하는 표현을 우선한다.

### 나쁜 표현

> 이 구조는 단순한 데이터 저장소를 넘어 조직의 지식을 연결하는 두뇌 역할을 수행합니다.

### 좋은 표현

> 업무 데이터 간 연관관계를 관리할 수 있도록 통합 메타데이터 구조를 적용한다.

### 나쁜 표현

> 사용자 경험을 극대화하기 위한 강력한 기반을 제공합니다.

### 좋은 표현

> 사용자가 필요한 정보를 빠르게 조회할 수 있도록 화면과 검색 구조를 단순화한다.

추상적인 표현 대신 무엇을, 왜, 어떻게 하는지를 적는다.

## 4. IT·개발자 방언 최소화

개발자끼리 사용하는 은어, 유행어, 과도한 영문 용어는 일반 업무 용어로 바꾼다.

| 개발자 용어 | 권장 표현 |
|---|---|
| 파이프라인 | 처리 절차, 처리 흐름 |
| 오케스트레이션 | 작업 통합 관리 |
| glue | 연계 기능 |
| source of truth | 기준 정보 |
| bootstrap | 초기 구성 |
| plug-in 방식으로 꽂는다 | 필요한 기능을 추가할 수 있도록 구성 |
| loose coupling | 시스템 간 의존성을 최소화 |
| fail fast | 오류를 조기에 확인 |
| graceful degradation | 일부 장애 시에도 가능한 기능은 계속 제공 |
| single pane of glass | 통합 관리 화면 |

단, API, DB, AI, ERP, WAS 등 업계에서 일반적으로 사용하는 용어까지 억지로 번역하지 않는다.

전문용어가 꼭 필요한 경우에는 처음 한 번만 간단하게 의미를 설명한다.

## 5. 개발 비유와 과장 표현 제거

다음과 같은 표현은 사용하지 않는다.

- 두뇌
- 혈관
- 심장
- 신경망
- 레고 블록처럼
- 퍼즐처럼
- 엔진
- 허브
- 게임 체인저
- 강력한
- 획기적인
- 혁신적인
- seamless
- robust
- scalable

해당 표현이 실제 기술적 의미를 갖는 경우를 제외하고 업무적이고 구체적인 표현으로 바꾼다.

## 6. 읽기 쉬운 문장으로 수정

한 문장에 여러 내용을 넣지 않는다.

한 문장은 가급적 하나의 주장이나 사실만 전달한다.

긴 문장은 2~3개로 나눈다.

명사만 연속되는 문장을 피한다.

### 나쁜 표현

> 사용자 권한 기반 데이터 접근 통제 및 메뉴 화면 기능별 정책 적용 구조 제공

### 좋은 표현

> 사용자 권한에 따라 조회 가능한 데이터를 제한한다. 메뉴와 기능에 대해서도 별도의 권한을 설정할 수 있다.

## 7. 지나친 목차화와 나열 제거

모든 내용을 `1`, `1.1`, `1.1.1` 형태로 세분화하지 않는다.

관련된 내용은 문단으로 묶고, 실제 비교·조건·절차처럼 목록이 필요한 경우에만 표나 목록을 사용한다.

비슷한 의미의 장점이나 특징을 여러 항목으로 부풀리지 않는다.

내용이 없는 제목은 삭제한다.

## 8. 중복 제거

앞에서 설명한 내용을 표현만 바꾸어 다시 설명하지 않는다.

개요, 핵심 포인트, 상세 설명, 요약, 결론에서 같은 내용이 반복되면 한 곳으로 통합한다.

분량을 유지하기 위해 같은 내용을 반복해서는 안 된다.

## 9. 근거 없는 판단 제거

다음과 같은 표현은 객관적인 근거가 있는 경우에만 사용한다.

- 효율적이다
- 최적이다
- 안정적이다
- 성능이 뛰어나다
- 확장성이 높다
- 비용이 절감된다
- 생산성이 향상된다

근거가 없다면 실제 구조나 효과를 직접 설명한다.

### 나쁜 표현

> 확장성이 뛰어나다.

### 좋은 표현

> 기능을 모듈 단위로 추가할 수 있어 기존 기능의 수정 범위를 줄일 수 있다.

## 10. 보고서의 핵심을 앞에 배치

각 절은 가능하면 다음 순서로 작성한다.

1. 현황 또는 문제
2. 적용 방안
3. 주요 내용
4. 영향 또는 고려사항

기술 설명 자체가 목적이 아니라 의사결정에 필요한 내용을 우선한다.

## 11. 독자가 알아야 할 수준까지만 기술

내부 구현 세부사항이 의사결정과 관계없다면 삭제하거나 별도 기술 부록으로 이동한다.

본문은 다음 질문에 답할 수 있어야 한다.

- 현재 어떤 문제가 있는가?
- 무엇을 변경하려는가?
- 왜 필요한가?
- 기존 방식과 무엇이 달라지는가?
- 업무 또는 시스템에 어떤 영향이 있는가?
- 비용, 일정, 위험 요소는 무엇인가?
- 결정하거나 확인해야 하는 사항은 무엇인가?

## 12. 문체

기본 문체는 국내 기업의 기획서, 제안서, 검토보고서 수준으로 작성한다.

과도하게 학술적이거나 홍보 문구처럼 작성하지 않는다.

간결하지만 내용이 지나치게 축약되지 않도록 한다.

가능하면 다음과 같은 표현을 사용한다.

- 적용한다
- 구성한다
- 제공한다
- 관리한다
- 연계한다
- 확인이 필요하다
- 별도 협의가 필요하다
- 다음 단계에서 검토한다

## 13. 최종 정리

수정이 완료되면 문서 자체만 출력한다.

다음 내용은 출력하지 않는다.

- 무엇을 수정했는지에 대한 설명
- AI가 수행한 작업 목록
- 편집 과정
- “수정 완료했습니다”와 같은 메시지
- 자체 평가
- 프롬프트 또는 작업 지침
- 원문과 수정본 비교

최종 산출물은 작성 과정이 전혀 드러나지 않는 완성된 업무 문서여야 한다.

## 14. 최종 점검 기준

이 문서를 읽는 사람이 “AI가 작성한 문서 같다”고 느낄 만한 문장이 있으면 다시 수정한다.

특히 다음 세 가지를 마지막에 다시 점검한다.

1. 이 표현을 실제 회사 직원이 보고서에 쓸 가능성이 높은가?
2. 개발자가 아닌 사람이 읽어도 의미를 바로 이해할 수 있는가?
3. 이 문장이 없어져도 의미가 같다면 삭제할 수 있는가?

세 질문 중 하나라도 문제가 있으면 해당 문장을 수정하거나 삭제한다.

## 15. 잘 안 읽히는 문장 네 가지 (필수 — 문서 · 화면 문구 · 채팅 · 생각 모두)

아래 네 형태는 쓰지 않는다. 이미 쓴 글에서 보이면 고친다.

### (1) 연결 단어 생략
앞뒤 문장의 관계(이유 · 결과 · 대조 · 순서 · 조건)를 잇는 말을 빼면 읽는 사람이 관계를 짐작해야 한다. 관계가 있으면 「그래서」「그런데」「다만」「먼저 · 그다음」「~면」「~라서」처럼 드러낸다.
- 나쁜 예: 조회가 느리다. 캐시를 둔다.
- 좋은 예: 조회가 느려서 캐시를 둔다.
- 짧은 목록 항목처럼 서로 독립된 사실은 연결어 없이 둔다. 관계가 있는 두 사실을 따로 떼어 놓지 않는다.

### (2) 사물의 지나친 의인화
사물 · 기능 · 코드에 사람의 갑작스러운 동작(삼키다 · 먹다 · 꼬리를 물다 · 숨 쉬다 · 죽이다 · 살아나다 · 지켜보다 · 말하다)을 붙이지 않는다. 실제로 일어나는 일을 쓴다.
- 나쁜 예: 함수가 에러를 삼킨다. / 대화가 제 꼬리를 문다. / 탭이 서버를 깨운다.
- 좋은 예: 함수가 오류를 잡고 아무 기록도 남기지 않는다. / 같은 질문과 답이 반복된다. / 탭을 열면 서버에 요청을 보낸다.

### (3) 명사 이어 붙이기
명사를 세 개 이상 조사 없이 잇지 않는다. 조사 · 어미를 넣어 관계를 드러내거나 문장으로 푼다.
- 나쁜 예: 공포 영화 배경음악 생성기 / 사용자 권한 기반 데이터 접근 통제
- 좋은 예: 공포 영화에 쓸 배경음악을 만드는 도구 / 사용자 권한에 따라 볼 수 있는 데이터를 제한한다
- 업계에서 한 낱말처럼 굳은 이름(제품명 · 메뉴 이름 · 정식 기능명)은 예외지만, 설명 문장에서는 풀어 쓴다.

### (4) 짝이 되는 말 멀리 띄우기
주어와 서술어, 수식어와 꾸밈 받는 말 사이를 길게 벌리지 않는다. 사이에 긴 수식 · 괄호 · 나열이 끼면 문장을 나누거나 순서를 바꾼다.
- 나쁜 예: 서버는 관리자가 설정 화면에서 지정한 시각에 맞춰 매달 첫날 지난달 로그를 모아 분석한 결과를 PDF 로 만들어 보낸다.
- 좋은 예: 서버는 매달 첫날 지난달 로그를 모아 분석한다. 그 결과를 PDF 로 만들어, 관리자가 설정 화면에서 지정한 시각에 보낸다.

### 점검
글을 마치면 네 가지를 한 번 더 훑는다: 관계가 빠진 문장 사이가 있는가 · 사물이 사람처럼 움직이는가 · 명사가 셋 이상 붙어 있는가 · 주어와 서술어가 멀리 떨어져 있는가.
