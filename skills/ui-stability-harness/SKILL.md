# UI 안정성 하네스

## 1. 왜 필요한가

단위 시험과 기존 종단 시험은 «요소가 DOM 에 있는가 · API 응답이 맞는가» 를 본다. 실사용 화면 결함은 대부분 그 바깥에서 생긴다. 실제 사례(4개월 222건)에서 기존 자동 시험이 먼저 잡은 결함은 8% 였다.

- jsdom 은 레이아웃 · 쌓임 순서 · ResizeObserver 를 계산하지 않는다. 겹 순서 · 깜빡임 · 캔버스 결함은 원리적으로 못 잡는다.
- 종단 시험은 `toBeVisible()` 로 끝난다. 「있다」 만 확인하고 「보인다 · 가려지지 않았다 · 잘리지 않았다」 는 확인하지 않는다.
- 로컬 시드는 100ms 안에 응답한다. 로딩 창이 짧아 전환 깜빡임이 드러나지 않는다.
- 합성 이벤트(`dispatchEvent`)는 사람 속도의 끌기 · 포인터 이탈 결함을 재현하지 못한다.

이 하네스는 **「보이는가 · 가려졌는가 · 유지되는가 · 흔들리는가 · 얼마나 걸리는가」** 를 판정한다. DOM 존재는 판정 근거가 아니다.

## 2. 구조 — 두 계층

| 계층 | 범위 | 깊이 | 입력 |
|---|---|---|---|
| 자동 탐색 계층 | 코드에서 센 **전 화면 × 전 상호작용 요소** | 얕게(공통 불변식) | 화면 목록 생성기가 만든 `screens.json` |
| 진입점 레지스트리 | 손으로 등록한 «여는 동작» | 깊게(시나리오별 드라이버) | `registry.ts` + `drivers.ts` |

자동 탐색이 넓이를, 레지스트리가 깊이를 맡는다. 둘 다 같은 판정 함수와 같은 증거 형식(2x 캡처 + 판정 근거 JSON)을 쓴다.

### 2.1 자동 탐색 계층

1. **화면 목록 자동 수집**(`collect-screens.mjs`) — 라우터 정의 · 관리자 절 · 설정 카드 앵커 · 매뉴얼 절 · 단계 · 서랍 · 모달 파일 · 패널 탭을 **코드에서 세어** `screens.json` 을 만든다. 화면마다 URL, 앞선 조작(click), 필요한 시드(setup), 역할(role)을 적는다. 매개변수 라우트는 시드 대표 id 로 채운다(`ROUTE_FILL`).
   - **정적 가드**: 라우터에 새 라우트가 생겼는데 `ROUTE_FILL` 에 들어가는 방법이 없거나, 커밋된 `screens.json` 과 지금 코드가 다르면 실패한다. 새 화면이 목록에 반드시 들어온다.
   - 모달은 URL 이 없다 — 클릭 탐색이 연 표면 안에서 그 모달 파일의 testid(markers)를 보면 «방문» 으로 센다.
2. **요소 자동 수집과 공통 불변식**(`explore-lib.browser.js` + `explore.ts`) — 화면을 열 때마다 `button, a[href], [role=button|menuitem|tab|link|switch|checkbox|combobox|…], input, select, textarea, [tabindex]` 를 모두 모으고 요소마다 I1 · I11 · I12 · I17 · 이름 · 링크 대상을 본다. 화면 단위로 I12(문서) · I14 · I15 · I25 · I19 재료를 남긴다.
3. **클릭 탐색**(안전한 것만) — 파괴 · 외부 동작은 규칙으로 뺀다(testid 규칙 · 「삭제 · 저장 · 게시 · 보내기 …」 문구 · danger 변형 · submit · `target=_blank` · 입력 계열). **즉시 저장되는 설정도 뺀다**: 토글(aria-pressed · aria-checked) · 선택 묶음(radiogroup · 세그먼트 · 견본) · 증감 단추. 남은 단추를 `page.mouse` 로 실제로 눌러 I14 · 깨짐 · 열린 표면의 I1 · I9 · I10 · I22 를 보고 Esc · 뒤로로 되돌린다. 같은 컴포넌트(탑바 단추 등)는 실행당 한 번만 누른다.
   - **상태 지킴**: 화면마다 개인 설정 · 공용 설정 응답을 앞뒤로 비교해 바뀌면 `MUTATION` 위반으로 남기고 개인 설정은 되돌린다. 실제 사례: 선택 단추 하나가 시험 계정의 패널 배치를 바꿔 다른 시험의 모달이 열리지 않았다.
   - 깨짐 판정은 «같은 주소에서» 요소 수가 크게 줄었을 때만 — 다른 화면으로 넘어가면 요소 수 비교는 뜻이 없다.
4. **커버리지 지표**(`coverage-report.mjs`) — 화면 커버리지(탐색/전체) · 요소 커버리지(검사/발견) · 클릭 커버리지(누름/대상) · 불변식별 위반 · 위반 묶음(같은 컴포넌트의 반복은 하나로) · 추정 원인 파일:줄. 결과는 `coverage/uistab/*.json` 과 `docs/testing/ui-coverage.md`.
5. **래칫** — 처음 돌리면 위반이 많다. 고치지 않고 **베이스라인으로 잠근다**(`--update-baseline`). 이후 베이스라인에 없는 새 위반 · 커버리지 하락만 실패시킨다. 고치면 베이스라인을 줄인다.

### 2.2 진입점 레지스트리

- 한 항목 = 「여는 동작」 하나: id · 진입 경로(사람이 따라 할 문장) · 기대 표면 · 적용 불변식 · 조건 · 원장 케이스 ID · 그 표면을 그리거나 여는 소스 파일(R/V) · 잡는 결함 번호 · 보류(fixme: 결함 ID · 사유 · 조합).
- 레지스트리 파일은 **런타임 import 가 없는 순수 데이터**로 둔다 — 정적 가드가 Node 로 직접 읽는다. 실제 입력은 `drivers.ts` 에 같은 id 로.
- **누락 가드**(`check-surface-registry.mjs`): 앱 코드의 «표지» 를 파일별로 세어 베이스라인보다 늘면 실패.
  - 여는 호출: 프로그램으로 패널 · 도움말 · 투어를 여는 함수 호출, 딥링크 이동(`navigate('/…#앵커')` · `href="/…#앵커"`).
  - 떠 있는 표면: `createPortal(` · `<Teleport` · `role="menu|dialog|alertdialog|tooltip"` · `aria-modal` · 프로젝트의 팝오버 · 모달 · 툴팁 클래스 · `<…Drawer` 컴포넌트.
  - 베이스라인 갱신은 레지스트리 `sources` 에 오른 파일만 수를 올릴 수 있다. 등록하지 않은 파일의 증가는 거부한다. 표지 종류를 바꿨을 때만 베이스라인을 지우고 한 번 다시 잠근다.
  - 레지스트리 무결성도 본다: id 중복 · 드라이버 없음 · 원장 짝 · 낡은 sources · 결함 ID 없는 보류.

### 2.3 조건 축

뷰포트(390 · 1024 · 1440 · 2560) × 사이드바(저장값 · 최소 폭) × 패널 고정(ON · OFF) × 테마(라이트 · 다크) × 배치(창 · 도킹) × 느린 환경(응답 600ms · CPU 4배)을 전 조합으로 돌리면 항목당 수십 회다. **축마다 모든 값이 한 번 이상 나오게** 조건을 줄이고, 결함이 났던 특정 조합(예: 좁은 사이드바 + 고정 ON)은 반드시 조건에 넣는다. 병합 관문은 core 하나, 나머지는 야간.

## 3. 불변식

판정은 모두 «화면에 그려진 결과» 다. 실패하면 2x 캡처(CDP `Page.captureScreenshot` 의 `clip.scale=2`)와 판정 근거 JSON(elementFromPoint 결과 · 쌓임 순서 · 시간 기록 · 측정값)을 시험 결과에 첨부한다.

| # | 이름 | 판정 | 흔한 함정 |
|---|---|---|---|
| I1 | 가시성 · 가림 없음 | 자리 잡은 뒤(연속 3프레임 같은 상자) 네 모서리(안쪽 inset) · 중심의 `elementFromPoint` 가 자신(또는 자손). 뷰포트 안. 등록된 딤 층은 쌓임 순서를 따로 계산 | `pointer-events:none` 딤 · 스포트라이트 그림자는 elementFromPoint 를 통과한다 → 쌓임 순서 계산 필요. 둥근 단추는 모서리 inset 을 반지름의 0.35+2px 로. 스크롤 막대 자리는 client 상자로 뺀다. 입력 칸 안 증감 단추처럼 같은 부모의 조작 요소가 모서리를 덮는 복합 컨트롤은 제외 |
| I2 | 열림 유지 | 프로그램으로 연 패널이 포인터를 화면 여러 곳으로 실제로 옮기는 동안 1,000ms 열려 있다(페이지 안 rAF 관찰) | 열 때 포인터가 이미 패널 자리 안이면 «밖→안» 재진입까지 붙들어야 한다 |
| I3 | 겹 순서 | 딤 · 투어가 떠 있는 동안 새로 열린 표면은 딤 위에 그려지거나 아예 열리지 않는다. 딤이 없으면 전제 실패 | 시험이 딤을 못 띄웠는데 통과하는 일을 막는다 |
| I4 | 핵심 버튼 접근성 | 어떤 표면이 떠도 탑바 버튼 가운데가 그 버튼 | 모달 딤 · 가벼운 닫기 막은 사유를 적어 예외 등록 |
| I5 | 흔들림 | 끌기 · 타이핑 한 걸음마다 상자를 재 프레임 간 이동량(포인터 이동량을 뺀 «남는 흔들림») | 줄 경계 1~2px 맞닿음은 겹침이 아니다 |
| I6 | 성능 예산 | 실제 누르기(페이지 안 pointerdown)부터 첫 의미 있는 표시까지 ms, 예산은 한 파일 | 서버 캐시 상태에 따라 콜드 · 웜이 갈린다 — 둘 다 적는다 |
| I7 | 앵커 이동 | 「…열기 · 설정 열기」 로 도착한 화면에서 대상이 뷰포트 안 + 초점 또는 강조 | 강조는 잠깐이다 — 4초 안에 한 번 |
| I8 | 레이아웃 정렬 | (프로젝트별 — 안내선 · 열 정렬) | |
| I9 | 초점 관리 | 열면 초점이 표면 안 · 모달은 Tab 이 밖으로 새지 않음 · 닫으면 연 단추로 복귀 | 키보드로 연 경우(⌘K)는 복귀 대상이 단추가 아니다 |
| I10 | Esc 계층 | Esc 한 번에 맨 위 표면 하나만 닫힘 · 아래 표면은 남음 | 문서 keydown 하나로 모든 층을 닫는 구현이 흔하다 |
| I11 | 잘림 + 단서 | 말줄임(`text-overflow` · line-clamp)이 걸린 글자에 title · aria-label · describedby, 없으면 실제 호버로 툴팁(`role=tooltip`)에 전체 글자가 뜨는지 | JS 툴팁은 정적으로 못 본다 → 호버로 확인. 호버 수는 화면당 상한 |
| I12 | 가로 넘침 없음 | 390 · 1024 · 1440 · 2560 에서 문서 가로 스크롤 없음 · 요소가 뷰포트 가로 밖으로 나가지 않음(가로 스크롤 상자 안은 제외) | 원인 요소는 «가장 오른쪽 요소» 로 근거를 남긴다 |
| I13 | 클릭 관통 없음 | 딤 · 오버레이를 눌렀을 때 그 점의 첫 조작 요소가 pointerdown · click 을 받지 않음 | `elementsFromPoint` 는 `pointer-events:none` 층을 빼고 돌려준다 — 관통이면 맨 위가 곧 아래 요소다 |
| I14 | 콘솔 · 예외 0 | 상호작용 동안 console.error · 처리 안 된 예외 0. 알려진 예외는 파일(사유 필수) | 크로미움은 처리 안 된 Promise 거부를 «Uncaught (in promise)» 콘솔 오류로 낸다 |
| I15 | 요청 폭주 없음 | 화면 열기 · 누르기 한 번 사이 같은 요청(방법+경로+쿼리)이 상한(3) 이하 · 보이지 않는 카드 요청 0 | StrictMode 이중 실행 · 썸네일 카드마다 요청 |
| I16 | 새로고침 · 딥링크 복원 | 해시 · 쿼리 딥링크로 들어오면 대상이 보이고, 새로고침 뒤 열린 상태 · 선택이 규칙대로 복원 | 접힌 아코디언 안 앵커는 «있지만 숨음» — 펼쳐야 한다 |
| I17 | 대비 | 조작 요소 글자 대비 4.5:1(큰 글자 3:1) 이상. 비활성은 WCAG 예외 | `oklch()` 같은 색 형식은 canvas 1×1 에 칠해 sRGB 로 읽는다. 배경은 조상 사슬을 겹쳐 칠한다. 배경 그림 · 그라데이션은 판정 불가로 뺀다 |
| I18 | 끌기 잔여물 없음 | 끌기를 마치거나 Esc 로 취소한 뒤 고스트 · 삽입 막대 · 끌기 표지 · `body user-select:none` · grabbing 커서가 없음 | iframe 편집기는 그 프레임도 본다 |
| I19 | R↔V 파리티 | 같은 시드 · URL · 뷰포트로 두 구현을 열어 접근성 트리(역할 · 이름) · 보이는 글자 줄 · 짝 testid 상자(±4px · ±2px)를 비교. 허용은 사유와 함께 파일로 | 상자는 «문서 좌표»(조상 스크롤 양을 더함)로 — 스크롤 위치가 다르면 전부 다르게 나온다. 숫자는 일반화 |
| I20 | 전환 깜빡임 · 레이아웃 이동 | 동작 전후 rAF 샘플러 + layout-shift 관찰: 빈 프레임(보이는 면적이 직전의 10% 미만 → 50% 이상 복귀) · CLS > 0.05 · 값 프레임(undefined · NaN) | 응답 600ms 지연 · CPU 4배 스로틀에서 잰다. «빈 화면으로 안정» 된 로딩 중에 측정을 멈추지 않게, 처음 면적의 절반 이상으로 돌아올 때까지 본다. 의도된 애니메이션은 reduced-motion 으로 끈다 |

## 4. 실제 입력 규칙

- 입력은 `page.mouse.move(x, y, { steps })` 여러 걸음 + `down` · `up`, `page.keyboard` 만 쓴다. **`dispatchEvent` · 합성 이벤트 · `locator.click({ force })` 를 쓰지 않는다** — 포인터 이탈 · 호버 열림 · 끌기 결함은 실제 입력에서만 재현된다.
- 미끄러져 들어오는 단추는 두 프레임 간격으로 잰 상자가 같아질 때까지 기다린 뒤 누른다.
- 고정 대기(`waitForTimeout`)를 쓰지 않는다. 페이지 안 rAF 관찰 · `waitForFunction(polling:'raf')` · networkidle 로 «조건» 을 기다린다.
- 브라우저는 **항상 헤드리스**로 띄운다. 재시도는 0 이다.
- 페이지 안 판정 코드는 순수 JS 파일 하나로 두고 글자 그대로 `page.evaluate(src)` 로 심는다 — 번들러의 이름 보존 도우미(`__name`)가 직렬화된 함수에 끼어 깨지는 일을 피한다.

## 5. 「실패하게 만들어 보는」 검증

불변식은 결함이 있을 때 실제로 실패해야 의미가 있다. 불변식마다 아래 중 하나 이상을 한다.

1. **수정 커밋 되돌리기** — 그 결함을 고친 커밋의 제품 소스만 역적용(`git show <커밋> -- apps | git apply -R`) → 스택 재빌드 → 해당 항목 실행 → 실패 확인 → 원복 → 재빌드 → 통과 확인. 정적 검사는 `git show <커밋>^:<파일>` 을 판정 함수에 넣어 본다.
2. **결함 주입 페이지** — 가짜 출처(`page.route('http://harness.test/**')`)에 결함 판과 고친 판 HTML 을 올려, 결함 판에서 실패 · 고친 판에서 통과하는 자체 시험을 둔다. 앱 · 스택과 무관해 빠르고 안정적이다(`templates/selftest.spec.ts`).
3. **전제 검사** — 스테일 서빙 감지(I26)는 표식 없는 옛 빌드를 서빙하는 상태에서 한 번 돌려 멈추는지 본다.

자체 시험은 두 번 연속 통과해야 한다(타이밍 판정의 경합을 걸러 낸다).

## 6. 깔기 절차(새 프로젝트)

1. `templates/` 를 프로젝트의 `e2e/helpers/ui-stability/` · `scripts/ui-stability/` 로 복사한다.
2. `collect-screens.mjs` 의 라우터 파일 경로 · 화면 종류 수집기 · `ROUTE_FILL`(매개변수 라우트의 대표 id · 역할 · 시드)을 채우고 `screens.json` 을 만든다. 화면 수를 세어 보고한다.
3. `explore-exclude.json`(클릭 제외) · `known-console.json`(알려진 콘솔 예외) · `ui-terms.json`(용어 사전) · `parity-allow.json`(R↔V 허용)을 사유와 함께 채운다.
4. `invariants.ts` 의 `DIM_SELECTORS` · `TOPBAR_EXEMPT_LAYERS` · `TOPBAR_BUTTONS` 를 프로젝트 선택자로 바꾼다.
5. 하네스 빌드에 빌드 표식(meta)을 넣는다(Vite 면 `transformIndexHtml`). 순회 사양 `beforeAll` 에서 I26 을 부른다.
6. 자체 시험(`selftest.spec.ts`)을 두 번 돌려 판정이 살아 있는지 확인한다.
7. 야간 전체를 한 번 돌리고 `coverage-report.mjs --update-baseline` 으로 잠근다. 위반 묶음 상위 10개는 2x 캡처 · 추정 원인 파일:줄을 붙여 수정 작업으로 나눈다.
8. 진입점 레지스트리는 오너 · 사용자 신고 결함마다 항목을 추가한다(잡는 결함 번호 기록).

## 8. 결함 이력 → 점검 항목 도출 절차

1. 자료를 모은다: fix 커밋(UI 경로) · CHANGELOG Fixed · 진행 기록의 사용자 신고 · 결함 대장 · e2e 원장의 defect 열 · 리뷰 보고서.
2. 같은 증상의 여러 커밋을 한 건으로 합치고, 화면 증상이 없는 서버 · 보안 결함은 뺀다.
3. **원인 유형**으로 분류한다(넘침 · 잘림 / 입력 · 초점 · Esc / 스테일 상태 / 시간 경합 / 겹 순서 / 캔버스 / 전환 깜빡임 / 정렬 / 대비 / 빈 · 오류 상태 / 파리티 / 접근성 / 성능 / 끌기 / 위치 기준 / 문구 / 빌드 / 스테일 서빙).
4. 결함마다 «지금 하네스로 잡히는가» 를 적는다. 안 잡히는 유형마다 **판정식 · 임계값 · 제외 규칙 · 시드 · 조건**을 갖춘 점검 항목을 제안한다.
5. 우선순위 = 잡았을 결함 수 × 심각도(백지 · 데이터 오독 · 조작 불가) ÷ 구현 비용. 전제 검사(스테일 서빙)와 정적 검사(빌드)는 비용이 낮아 먼저 넣는다.
6. 새 항목은 자체 시험(결함 주입)과 함께 넣고, 실제 결함 수정 커밋을 되돌려 실패를 확인한다.
7. 결함 유형 → 불변식 매핑표를 문서에 남긴다(번호가 다른 문서와 다르면 하네스 쪽을 정본으로 하고 대응표를 둔다).

## 9. 서브에이전트 지시문에 넣을 문구

```

5) 전체 순회 · 전 패키지 시험은 돌리지 않는다(메인이 취합 후 한 번).
페이지 입력은 page.mouse · page.keyboard 만 쓴다. dispatchEvent · force 클릭 · 고정 대기 금지.
```
